Demo 1 of 4

One VM, Side by Side

This demo counts every Prometheus series one idle VM produces, then live-migrates it and reads the transfer numbers off the same metrics store the pods already report to. The point is not a bigger number than vCenter, it is that every one of these series is joinable by ordinary PromQL against any label a pod or node already carries.

vm-demo, namespace demo-vmsOpenShift 4.20.32, OpenShift Virtualization 4.20.24live run 2026-09-11

kubevirt_vmi_* / kubevirt_vm_* metrics: GA virtctl live migration: GA Perses dashboards (COO 1.5+): GA, namespace-scoped

What this demo shows

Pick one VM nobody is doing anything interesting with, vm-demo in demo-vms, and ask three widening questions with plain PromQL: how many series does the VMI object itself expose, how many once you add the VM object's own series, and how many once you follow the pod label the virt-launcher pod carries and pull in every cAdvisor and kube-state-metrics series that comes with it. Then look at five panels that have no equivalent in vCenter or Aria at all: storage flush counters, memory available versus usable, the non_evictable gate behind the eviction alert, guest load from the in-guest agent, and the live migration data streams. Then trigger a real live migration with virtctl and watch the same counters move. Close by slicing the whole fleet, not just this one VM, by an arbitrary label with one line of PromQL, no PowerCLI script required.

The honest framing matters here. vCenter and Aria expose a fixed counter set per statistics level (1 through 4); it does not grow per VM the way a label-indexed store does, so a raw side-by-side count invites a fair "so what." The defensible claim is that every one of these series is independently queryable and joinable by arbitrary label right now, with the same query language you already use on every pod and node, not that OpenShift simply has more metrics than vCenter.

Why it matters next to vCenter

In vCenter or Aria, joining a VM's counters against its host, datastore, and cluster context means either the built-in correlation views Aria ships, or a PowerCLI script you write and maintain yourself. Here, the virt-launcher pod is joined to its VMI only by a label, vm.kubevirt.io/name, not an ownerReference, and that label is enough for a plain and on(namespace,pod) PromQL clause to pull in every cAdvisor and kube-state-metrics series for that pod. No new tool, no script, the same Thanos-querier your cluster team already uses for everything else.

Said plainly, so nobody has to guess later: vCenter and Aria still win on What-If capacity modelling, predictive DRS against forecast load, cost and chargeback reporting, and multi-year native retention. This demo does not touch any of those, and does not pretend to.

Before you start

Full prerequisites, install order, and every failure mode are in 0-prereqs-preflight-failure-modes.md. For this act specifically:

  • vm-demo running in demo-vms, marked LiveMigratable, and virtctl on PATH (the fallback is a VirtualMachineInstanceMigration object created with oc create).
  • qemu-guest-agent 10.0.0 or newer connected in the guest. Without it the guest load panels stay blank, not broken, just empty.
  • The kube_pod_labels allow-list for vm.kubevirt.io/name. Confirmed present on this cluster's kube-state-metrics right now (evidence/act1-metrics/SUMMARY.md, 02b-prereq-kube-pod-labels-check.json). This is not on by default on every OpenShift cluster, check it before you promise the pod join elsewhere.
  • schedstats=enable active on the workers, for the vCPU delay/wait panels. On this cluster it was turned on at runtime with sysctl, not the documented MachineConfig, so it works today but reverts on the next node reboot.
  • User workload monitoring enabled, so these queries can run against Thanos-querier at all.

Steps

  1. Open Observe, Metrics in the console. Run the first series-count query, VMI-scoped series only. 
    count({namespace="demo-vms", name="vm-demo", __name__=~"kubevirt_vmi_.*"})
    On this cluster right now that returns 61 (evidence/act1-metrics/SUMMARY.md, 01-count-vmi-only.json).
  2. Widen it to include VM-object-level series, the ones that exist even while the VM is stopped. 
    count({namespace="demo-vms", name="vm-demo", __name__=~"kubevirt_(vmi|vm)_.*"})
    Result: 72 (02-count-vmi-plus-vm.json).
  3. Try the full join through the virt-launcher pod, the version with group_left(), exactly as originally written. 
    count(
  {namespace="demo-vms", __name__=~"container_.*|kube_pod_.*"}
  * on(namespace,pod) group_left()
  (kube_pod_labels{namespace="demo-vms", label_vm_kubevirt_io_name="vm-demo"} * 0 + 1)
)
    This errors on this cluster: multiple matches for labels: grouping labels must ensure unique matches (03-count-full-join-via-pod.json). Two things stack here: a live migration was running at the time and left two virt-launcher pods carrying the same pod label, and separately, this Thanos build errors on any __name__=~"..." regex combined with group_left() even with a single unambiguous pod on both sides. Drop group_left() for a plain membership filter instead, since the panel only ever needs a count, not the multiplied values. 
    count(
  {namespace="demo-vms", __name__=~"container_.*|kube_pod_.*"}
  and on(namespace,pod)
  kube_pod_labels{namespace="demo-vms", label_vm_kubevirt_io_name="vm-demo"}
)
    This runs clean and returns 345 (03f-count-full-join-WORKING-and-based-equivalent.json), the full combined total. It is inflated right now by the stale second pod from the concurrent migration; expect it to roughly halve once that pod is garbage-collected.
  4. Still in Observe, Metrics, run the five panels with no vCenter equivalent, one query at a time. 
    sum(rate(kubevirt_vmi_storage_flush_requests_total{namespace="demo-vms",name="vm-demo"}[5m]))
kubevirt_vmi_memory_available_bytes{namespace="demo-vms",name="vm-demo"}
kubevirt_vmi_memory_usable_bytes{namespace="demo-vms",name="vm-demo"}
kubevirt_vmi_non_evictable{namespace="demo-vms"}
kubevirt_vmi_guest_load_1m{namespace="demo-vms",name="vm-demo"}
    Numbers for each are in the table below.
  5. Trigger the live migration and watch the transfer counters move. 
    virtctl migrate vm-demo -n demo-vms
    Then re-run these in Observe, Metrics, or leave a Perses/Grafana panel open on them: kubevirt_vmi_migration_data_processed_bytes, kubevirt_vmi_migration_data_remaining_bytes, kubevirt_vmi_migration_data_total_bytes, kubevirt_vmi_migration_disk_transfer_rate_bytes, all filtered to {namespace="demo-vms",name="vm-demo"}. Do not query kubevirt_vmi_migration_dirty_memory_rate_bytes on stage, it has an open accuracy bug and was deliberately left out of this run.
  6. Slice the whole fleet, not just vm-demo, by three different labels. 
    topk(5, sum by (namespace,name)(rate(kubevirt_vmi_cpu_usage_seconds_total[5m])))
count by (node)(kubevirt_vmi_info)
count by (label_tier)(kube_pod_labels{namespace="demo-vms", label_kubevirt_io="virt-launcher"})
    The last query is the "slice by a business label" case. kubevirt_vm_labels does not exist on this cluster; kube_pod_labels on the virt-launcher pod is the working path, and tier is the label these demo VMs actually carry.

What can go wrong

The full 14-row failure-mode table is in 0-prereqs-preflight-failure-modes.md. The ones that actually hit this act:

Status

  • GA: kubevirt_vmi_* and kubevirt_vm_* metrics, virtctl live migration, Cluster Observability Operator, Perses dashboards (COO 1.5+, namespace-scoped).
  • GA metric, open bug: the dirty-rate metrics exist and are GA, but carry a known accuracy bug and were not used for any number on this page.
  • Present but not persistent: schedstats=enable is live on this cluster's workers via a runtime sysctl, not the documented MachineConfig, so the vCPU delay/wait panels work today and will go blank after the next node reboot until the MachineConfig is applied.
  • Not on this build: the recording rules vmi:kubevirt_vmi_vcpu:count and namespace:kubevirt_vm:sum, and the metric kubevirt_vm_labels, none exist on OpenShift Virtualization 4.20.24. Use the raw-metric substitutes shown above.
  • Out of scope: PSI (psi=1) needs OpenShift 4.21 or newer, this act targets 4.20.

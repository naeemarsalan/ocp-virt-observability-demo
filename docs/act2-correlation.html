Alert to Log Line

This demo fires a real VMCannotBeEvicted alert on a VM that cannot live-migrate, then asks the Troubleshooting Panel to walk from that alert to the VM, its pod, its logs and its network flows, first on the korrel8r build OpenShift Virtualization ships today, then on the newer build running next to it. The one thing to take from the room: on the shipped engine that walk cannot even start from the alert, on the same cluster with a newer korrel8r image it takes 6.8 seconds end to end.

What this demo shows

Create vm-non-migratable in demo-vms with a ReadWriteOnce block disk and evictionStrategy: LiveMigrate. The disk can't be shared, so KubeVirt sets kubevirt_vmi_non_evictable to 1 and VMCannotBeEvicted fires about a minute later, a genuine, unmodified alert with a 1 minute for. Confirmed live: the VMI reached Running at 13:06:16Z, the alert first fired at 13:13:14Z, resolved briefly, then fired again at 13:24:44Z (evidence/demo-vms/SUMMARY.md, evidence/korrel8r-0.12/SUMMARY.md, reference-architecture.html). Show the dead end first: KubeVirt Top Consumers lists the VM by name with nothing to click through to its pod, the same gap Demo 1 flags (evidence/screenshots/SCREENSHOTS.md).

Open the Troubleshooting Panel (Application launcher, Signal Correlation) and paste the VMI's own korrel8r query into the Start Query box, Neighbours, 3 hops. On the shipped korrel8r 0.11.1 that reaches 12 node classes, VM down to Application logs (evidence/screenshots/SCREENSHOTS.md). Paste the alert's own query in instead and the same engine reaches only Alert and Metric, because AlertToVMI is not compiled into this build (evidence/troubleshooting-panel/SUMMARY.md). Run both queries against the upstream korrel8r 0.12.1 instance next to it, over its REST goals endpoint, and the alert query alone reaches VM, VMI, Pod, three Nodes, metric and log data in 6.8 seconds; the VMI query adds PVC, alert and netflow in 15.3 seconds (full counts in the tables below, evidence/korrel8r-0.12/SUMMARY.md, reference-architecture.html).

Why it matters next to vCenter

In vCenter, a VM's alarms already roll up against its host, cluster and datastore, because vCenter's inventory is a real, owned object tree, not a label join, so an alarm shows related context with no extra tooling. Aria Operations goes further, layering dynamic-threshold correlation and its own troubleshooting workbench on that tree, a more polished, more turnkey experience today than a rules engine that, on the build most customers run on day one, cannot walk from a firing alert to the VM at all.

Say that plainly before anyone has to ask: the GA Cluster Observability Operator ships korrel8r 0.11.1, and on this cluster the Alert to VM, Alert to VMI, VM to Alert, VMI to Alert and VMI to Logs rules simply are not in it (evidence/troubleshooting-panel/SUMMARY.md). What the walk buys once those rules exist is not a nicer picture than Aria's, it is that the same graph also reaches things Aria never sees, an arbitrary pod label, an OVN network flow, a Loki log line in a different namespace, through the same open rule mechanism every other object type in the cluster already uses. The claim for today is narrower: the VMI-to-pod-to-logs-to-flows leg already works on the shipped engine; the alert-to-VMI leg needs korrel8r 0.11.4 or newer, which the upstream 0.12.1 instance here demonstrates.

Before you start

Full prerequisites, install order, and every failure mode are in 0-prereqs-preflight-failure-modes.md. For this act specifically:

  • The demo-vms namespace and a StorageClass that can provision ReadWriteOnce, so the disk forces LiveMigratable=False regardless of backend.
  • The TroubleshootingPanel UIPlugin installed with Available=True. GA only from COO 1.3 on OpenShift 4.19+ (reference-architecture.html); confirm the minimum supported OpenShift version before the demo, it is not available on every earlier release.
  • LokiStack Ready in openshift-logging and Network Observability's own LokiStack Ready in netobserv, so the log and netflow domains have somewhere to query. Korrel8r doesn't error on a missing one, it silently omits the node.
  • Run korrel8r rules --config=/config/korrel8r.yaml -n '(Vm|Vmi|Vmim|Alert)' --long inside the pod days ahead, not hours ahead. Whether Alert to VMI exists depends on the pinned image tag, not anything visible in a ConfigMap.
  • For the upstream comparison, that instance's own route and a bearer token ($(oc whoami -t)).

Steps

  1. Create the non-migratable VM. 
    oc apply -f act2-02-recipe-a-vmcannotbeevicted.yaml
oc wait vmi/vm-non-migratable -n demo-vms --for=jsonpath='{.status.phase}'=Running --timeout=180s
oc get vmi vm-non-migratable -n demo-vms -o wide   # LIVE-MIGRATABLE column reads False
    The manifest sets accessModes: ["ReadWriteOnce"] on the DataVolumeTemplate and evictionStrategy: LiveMigrate (not LiveMigrateIfPossible) on the template spec, the two settings that force the block (evidence/demo-vms/SUMMARY.md).
  2. Watch VMCannotBeEvicted fire. Console: Observe, Alerting, Alerts. Set Project to All Projects first, this page shows nothing against the last-used project otherwise. Filter by alert name VMCannotBeEvicted, state Firing, and click the instance for demo-vms/vm-non-migratable.
  3. Show the dead end. Console: Observe, Dashboards, KubeVirt, Top Consumers. Switch the table to By VM, point at vm-non-migratable. There is nothing to click from the VM name to its pod, the pod carries only a label back to the VMI, not an ownerReference.
  4. Open the panel and paste the VMI query. Console: Application launcher (grid icon, top right), Signal Correlation. Click the expand chevron next to the time-range dropdown, a Start Query box appears with the placeholder domain:class:selector. 
    k8s:VirtualMachineInstance.v1.kubevirt.io:{"namespace":"demo-vms","name":"vm-non-migratable"}
    Leave Search Type on Neighbours, 3 hops, and click Search.
  5. Paste the alert query into the same panel instead. 
    alert:alert:{"alertname":"VMCannotBeEvicted","namespace":"demo-vms","name":"vm-non-migratable"}
    Click Search again. Same engine, same panel, a much smaller graph, this is the gap the rest of the demo explains.
  6. Run the same two queries against the upstream 0.12.1 engine, over its REST goals endpoint. 
    curl -sk -X POST "https://<cluster-domain>/api/v1alpha1/graphs/goals" \
  -H "Authorization: Bearer $(oc whoami -t)" -H "Content-Type: application/json" \
  -d '{"start":{"queries":["alert:alert:{\"alertname\":\"VMCannotBeEvicted\",\"namespace\":\"demo-vms\",\"name\":\"vm-non-migratable\"}"]},
       "goals":["k8s:VirtualMachineInstance.v1.kubevirt.io","k8s:Pod.v1","log:application","netflow:network","metric:metric","k8s:Node.v1"]}'

curl -sk -X POST "https://<cluster-domain>/api/v1alpha1/graphs/goals" \
  -H "Authorization: Bearer $(oc whoami -t)" -H "Content-Type: application/json" \
  -d '{"start":{"queries":["k8s:VirtualMachineInstance.v1.kubevirt.io:{\"namespace\":\"demo-vms\",\"name\":\"vm-non-migratable\"}"]},
       "goals":["k8s:Pod.v1","log:application","netflow:network","metric:metric","k8s:Node.v1","alert:alert","k8s:PersistentVolumeClaim.v1"]}'
    Each response's nodes array carries one entry per class reached with its own query string and result count, and edges names the rule that connects each pair (evidence/korrel8r-0.12/SUMMARY.md, goals-alert-to-all.json, goals-vmi-to-all.json).

Tried live, worth saying out loud rather than skipping: pasting AlertToVMI and VmiToLogs rules written in the 0.12 syntax into the operator's own korrel8r ConfigMap was reverted by the Cluster Observability Operator in under two minutes, and while the patched config was live it broke the panel outright, "Search Error: invalid rule AlertToVMI: function \"required\" not defined", because 0.11.1 lacks the template function the newer syntax uses. It needed a pod restart to come back clean. Not a fallback to demo live, it's proof the rule mechanism is a plain, extensible ruleset and that the real fix for the missing rules is a newer korrel8r image (evidence/troubleshooting-panel/SUMMARY.md, custom-rule-experiment-outcome.txt).

Status

  • GA: the COO 1.5.2 Troubleshooting Panel UIPlugin, and korrel8r 0.11.1's own VmToVmi, VmiToPod, VmiToNode, VmToPVC, plus the generic PodToLogs, PodToAlert, PodToNode, K8sSrcToNetflow and AllToMetric that carry the walk once it starts from a Kubernetes object.
  • Upstream, not in this image: AlertToVM, AlertToVMI, VmToAlert, VmiToAlert and VmiToLogs, shipped in korrel8r 0.11.4 and recompiled in 0.12.1, the build running alongside this cluster (104 rules total, 37 KubeVirt-specific, evidence/korrel8r-0.12/SUMMARY.md, rules-count.txt, reference-architecture.html).
  • Experimental: the REST goals walk and any panel pointed at that upstream instance, a separate deployment run side by side, not the shipped console experience.
  • Not a supported live fix: patching the operator's own korrel8r ConfigMap. It reverts in about two minutes and, until the pod restarts, breaks the panel outright (evidence/troubleshooting-panel/SUMMARY.md, custom-rule-experiment-outcome.txt).

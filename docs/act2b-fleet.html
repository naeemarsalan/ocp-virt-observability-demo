Still on the Old Image

After an OpenShift Virtualization upgrade, one gauge tells you how many running VMs are still on the old virt-launcher pod, and a label query tells you exactly which ones. The one thing to take away: the alert built to escalate this has been sitting Pending for a week on true data, not because the fleet is fine, but because the component reporting it keeps restarting and resetting its own clock.

21 outdated VMIs, 7 namespacesOpenShift 4.20.32, OpenShift Virtualization 4.20.24live run 2026-09-11

kubevirt_vmi_number_of_outdated metric: GA OutdatedVirtualMachineInstanceWorkloads alert rule: GA HyperConverged workloadUpdateStrategy field: GA on this cluster: alert stuck Pending, drain disabled

What this demo shows

OpenShift Virtualization 4.20.24 is installed and Succeeded on this cluster, but 21 running VMIs across 7 namespaces are still executing inside a virt-launcher pod built from the pre-upgrade image digest. A single gauge, kubevirt_vmi_number_of_outdated, has read 21 continuously for at least 7 days (evidence/fleet-beat/SUMMARY.md). A label query names every one of those 21 VMIs by namespace. Two virt-launcher image digests coexist cluster-wide right now, 22 pods on the old one and 11 on the current one, and the HyperConverged CR's workloadUpdateMethods field is an empty list, so nothing is moving any of the 21 off the old image on its own. The alert designed to escalate exactly this condition, OutdatedVirtualMachineInstanceWorkloads, has a 24-hour for clause and has been Pending, not Firing, the entire week, because both virt-controller replicas keep losing their leader-election lease and restarting, which resets the alert's 24-hour timer every time. This demo is entirely read-only: the patch that would enable draining is shown and explained, never run.

Why it matters next to vCenter

vCenter tracks the equivalent drift per VM, not per fleet: the VMware Tools status column shows which VMs are running an old Tools build, and the VM hardware version shows which VMs are on an old compatibility level, both visible one VM at a time in the UI or pulled fleet-wide with a PowerCLI script you write and maintain. vSphere Lifecycle Manager adds cluster-level compliance and remediation, but it targets ESXi hosts and their image, not a per-VM helper process the way virt-launcher works. What OpenShift Virtualization has that vCenter does not is a single scrapeable, alertable number for the whole fleet, kubevirt_vmi_number_of_outdated, sitting in the same Prometheus every other cluster alert already comes from, plus one declarative field, workloadUpdateMethods, that can drain the fleet automatically once it's turned on. Said plainly: this cluster's own alert on that number hasn't fired all week, so the fair comparison here is a fleet gauge and a documented lever, not a working alarm, and that gap is exactly what this demo has to say out loud.

Before you start

Full prerequisites, install order, and every failure mode are in 0-prereqs-preflight-failure-modes.md. For this act specifically:

  • User workload monitoring enabled, so kubevirt_vmi_number_of_outdated and the ALERTS/ALERTS_FOR_STATE series can be queried at all.
  • Read access to VMIs and pods cluster-wide (oc get vmi -A, oc get pods -A -l kubevirt.io=virt-launcher) and to the HyperConverged CR in openshift-cnv.
  • No demo-specific VM setup: unlike Demo 1 and Demo 2, the 21 outdated VMIs here are pre-existing workloads belonging to other users on this shared cluster, not anything this track created. demo-vms does not appear in the outdated list (evidence/fleet-beat/SUMMARY.md).
  • This is a read-only track. The one command that would change cluster state, the drain patch in step 6 below, is shown for reference only and was never executed, under the same guardrail that rules out patching the HyperConverged CR on a shared cluster.

Steps

  1. Query the fleet-wide gauge. 
    kubevirt_vmi_number_of_outdated
    Reads 21, reported by the current virt-controller leader pod, virt-controller-7b86885b64-p4m8c (evidence/fleet-beat/SUMMARY.md, 01-outdated-current.json).
  2. Pull its 7-day history at 1-hour resolution, 2026-09-04 13:46 UTC to 2026-09-11 13:46 UTC. 
    kubevirt_vmi_number_of_outdated
# query_range, step=1h, start=2026-09-04T13:46:00Z, end=2026-09-11T13:46:00Z
    Every sample from both virt-controller replicas over that window reads 21. Flat for at least a week (02-outdated-7d-1h.json).
  3. List the outdated VMIs by name and namespace. 
    oc get vmi -A -l kubevirt.io/outdatedLauncherImage
    Returns exactly 21 VMIs (03-outdated-vmi-full.json), matching the gauge. Grouping the namespace column gives the per-namespace counts in the table below; the grouping step itself is a plain sort | uniq -c over the namespace/name output, illustrative of method rather than a captured command (03-outdated-vmi-count-per-namespace.txt holds the actual counts).
  4. Show the two virt-launcher image digests coexisting. 
    oc get pods -A -l kubevirt.io=virt-launcher \
  -o custom-columns=NAMESPACE:.metadata.namespace,NAME:.metadata.name,IMAGE:.spec.containers[?(@.name=="compute")].image
    22 pods carry the old digest (sha256:1b8b24e4...254e918c), 11 carry the current one (sha256:c88c03c9...ea529430e), matching the CSV's relatedImages entry for virt-launcher (09-virt-launcher-pods-full.json, 09b-virt-launcher-image-counts.txt, 08-csv-full.json).
  5. Show that nothing is set up to move them. 
    oc get hyperconverged kubevirt-hyperconverged -n openshift-cnv -o jsonpath='{.spec.workloadUpdateStrategy}'
    Returns batchEvictionInterval: 10m0s, batchEvictionSize: 1, workloadUpdateMethods: [] (07-hyperconverged-full.json). An empty method list means HCO will never migrate or evict a single one of the 21 on its own.
  6. Show the patch that would drain them. Documented only, not run on this cluster. 
    oc patch hco kubevirt-hyperconverged -n openshift-cnv --type=merge \
  -p '{"spec":{"workloadUpdateStrategy":{"workloadUpdateMethods":["LiveMigrate"]}}}'
    This would batch-migrate outdated, migratable VMIs one every 10 minutes under the CR's current batchEvictionSize/batchEvictionInterval. VMIs that cannot live-migrate need Evict added to the same list too, a real interruption, not a migration, which is why it is not on by default (12-patch-NOT-RUN-drain-outdated.txt). This is a cluster-wide field in openshift-cnv, not the demo's own namespace, and touches 21 VMIs belonging to other users, which is why this step is shown and not executed.
  7. Check the alert's own state, then check why it never moves. 
    ALERTS{alertname="OutdatedVirtualMachineInstanceWorkloads"}
ALERTS_FOR_STATE{alertname="OutdatedVirtualMachineInstanceWorkloads"}
oc get pods -n openshift-cnv -l kubevirt.io=virt-controller
    The alert is pending, not firing, severity warning (04/05 files). The two virt-controller pods have restarted 106 and 105 times respectively over a 30-day pod age (06d-virt-controller-pods.txt); the crash log shows a leader-election lease-renewal timeout followed by leaderelection lost (06e-virt-controller-p4m8c-full.json). A 7-day range query on ALERTS_FOR_STATE shows the alert's pending-since timestamp has reset 36 times across both replicas in that window (10-ALERTS_FOR_STATE-7d-history.json, 11-pending-resets-analysis.txt).

Do not promise this alert will reach Firing on a fixed schedule. The naive read of "pending since 13:45:44Z today" says Firing at 2026-09-12T13:46 UTC, but the condition has actually been true, unbroken, for at least 7 days already, and the timer has reset 36 times in that window without ever getting close. If the virt-controller crash-loop is fixed, expect Firing about 24 hours after that fix, not before, and not on the schedule the current pending timestamp alone implies. Demo the gauge and the label query as the reliable signals; treat the alert as a live illustration of why an alert can be true and silent at the same time.

What can go wrong

The full 14-row failure-mode table is in 0-prereqs-preflight-failure-modes.md. The ones that actually hit this act:

SymptomRoot causeWhat to do
The 24-hour outdated-workloads alert never reaches Firing, in either direction of the demoThe alert's own for: 24h clause means it cannot fire within a live session even when staged a day ahead; on this cluster it additionally never fires at all in practice, because both virt-controller replicas restart on leader-election lease-renewal failures and every restart resets the 24h pending timer (confirmed live: 106 and 105 restarts, 36 timer resets in 7 days)Never wait for the alert, here or on any other cluster. Graph kubevirt_vmi_number_of_outdated and run oc get vmi -A -l kubevirt.io/outdatedLauncherImage instead; call the alert a 24-hours-later escalation that this cluster's controller instability keeps resetting, not a broken feature.
A merge-patch against the HyperConverged CR looks like it worked but the field silently stays unsethco.kubevirt.io serves two API layouts: v1beta1 puts workloadUpdateStrategy at the top of spec (what this cluster uses and what Red Hat's docs show for 4.9-4.21); v1 nests it under spec.virtualization. A patch shaped for the wrong layout is silently prunedCheck oc get hyperconverged kubevirt-hyperconverged -n openshift-cnv -o jsonpath='{.apiVersion}' before writing any patch, and use the matching path. This cluster confirmed v1beta1, the top-level layout shown in step 5 and 6 above.
batchEvictionSize/batchEvictionInterval look like they should pace the drain, but a live-migratable VM rolls over instantly once workloadUpdateMethods is turned onThose two fields apply only to the Evict method, never to LiveMigrate, which is what actually moves the 21 outdated-but-migratable VMIs hereDon't promise a paced rollout for the migratable majority of this fleet; the pacing only matters for the subset that would need Evict (non-migratable outdated VMIs, none of which are in this list).

Status

  • GA: kubevirt_vmi_number_of_outdated, the OutdatedVirtualMachineInstanceWorkloads alert rule, and the HyperConverged workloadUpdateStrategy/workloadUpdateMethods field.
  • Working as designed, on this cluster: the gauge and the label query, both confirmed accurate and stable for 7 straight days.
  • Not doing anything on its own: workloadUpdateMethods is an empty list on this cluster, so none of the 21 outdated VMIs will move without the patch in step 6, which was never run.
  • Stuck, on this cluster specifically: the alert has been Pending, not Firing, for at least 7 days, because both virt-controller replicas keep restarting on leader-election failures and resetting the alert's 24-hour timer. This is a property of this cluster's controller stability, not of the alert rule itself.

The Rule Graph, Not a Guess

This demo asks the exact question Act 2 asked, from a firing alert to the VM, its pod and its logs, but sends it as plain JSON-RPC to korrel8r's own MCP server instead of clicking through the console, no LLM in the loop, just curl. The one thing to take from the room: the agent walks the rule graph; it does not guess, it reads the query and count korrel8r already computed for each class and asks for exactly that, and the GA console build answers the same request with two classes instead of six because the rule that crosses from alert to VMI hasn't shipped there yet.

korrel8r MCP server: experimental upstream since v0.10.0 Standalone MCP server: Red Hat has said it will not productize this GA COO 1.5.2 (korrel8r 0.11.1) also serves /mcp, incomplete rule set Lightspeed console integration: roadmap, targeted OCP 5.1

What this demo shows

A separately deployed upstream korrel8r 0.12.1 instance, driven with nothing but curl and JSON-RPC 2.0 bodies over the MCP "streamable HTTP" transport. initialize returns serverInfo.version 0.12.1 and a free-text instructions field that tells a caller how to use the tools: call list_domains, then help, then create_goals_graph or create_neighbors_graph, the server documents its own workflow (evidence/act3-mcp/01-initialize-response.pretty.json). tools/list comes back with 8 tools: create_goals_graph, create_neighbors_graph, get_console, get_objects, help, list_domain_classes, list_domains, show_in_console (evidence/act3-mcp/03-tools-list-response.pretty.json). Only three of those eight were actually called in this run, list_domains, create_goals_graph and get_objects; list_domain_classes and help exist but weren't exercised, and get_console/show_in_console are covered under Status below.

list_domains reports 8 domains, each with its backing store address: alert (Alertmanager plus Thanos), incident (no store configured), k8s, log (the logging LokiStack gateway), metric (Thanos), mock, netflow (the NetObserv LokiStack gateway, but its own store self-reports 403 Forbidden: You don't have permission to access this tenant) and trace (evidence/act3-mcp/04-tools-call-list_domains-response.pretty.json).

The real walk is create_goals_graph, started from the firing VMCannotBeEvicted alert on vm-non-migratable, with goals set to the VMI, the pod, application logs and metrics. The response's nodes array carries one entry per class actually reached, each with the concrete query and result count that produced it: alert 1, VMI 1, VM 1, Pod 1, metric 296 (three queries, 100 plus 100 plus 96), log 200 (two queries of 100 each). The edges array names which class fed which, alert:alert to k8s:VirtualMachineInstance.v1.kubevirt.io to k8s:Pod.v1 to log:application, plus a separate edge straight from the alert to metric and to the owning VM (evidence/act3-mcp/05-tools-call-create_goals_graph-response.pretty.json). The graph response itself doesn't print a rule name against each edge, that class-to-class path is what korrel8r rules --long would show as the named rules AlertToVMI, VmiToPod and VmiToLogs, part of the 37 KubeVirt rules out of 104 total on this upstream build (reference-architecture.html), versus 4 KubeVirt rules out of 47 on the GA image (evidence/troubleshooting-panel/SUMMARY.md).

Then get_objects turns two of those graph queries into real data. The pod query returns exactly 1 object: virt-launcher-vm-non-migratable-xrsp6 in demo-vms, phase Running, full spec and status (evidence/act3-mcp/06-tools-call-get_objects-pod-response.pretty.json). The log query, with constraint.limit set to 5, returns exactly 5 real log lines, newest first, for example "msg":"Polling command: [guest-fsfreeze-status]" at agent_poller.go:374 (evidence/act3-mcp/07-tools-call-get_objects-logs-response.pretty.json). Neither query was written by hand, both came verbatim off nodes the graph call had already produced.

Running the identical create_goals_graph request against the GA Cluster Observability Operator 1.5.2 image, the same korrel8r 0.11.1 the console in Act 2 runs, its /mcp endpoint answers too, after a bearer token (an unauthenticated probe gets HTTP 401). But the graph it returns has only two nodes: alert:alert (1) and metric:metric (136), the same alert PromQL expression as before but fewer series because this build's rule set differs, and it never crosses into VMI, pod or log space (evidence/act3-mcp/09 through 11-coo-0.11.1-*). This matches the rule gap Act 2 already shows in the console: AlertToVMI and VmiToLogs aren't compiled into 0.11.1.

Why it matters next to vCenter

Neither vCenter nor Aria Operations ships anything like an MCP interface today, there is no equivalent shipped, supported product surface for a script or an agent to ask "why is this VM alerting" and get back a graph of concrete queries. What Aria does have, and does ship, is its own troubleshooting workbench built on vCenter's owned inventory tree, dynamic-threshold correlation and root-cause suggestions inside a single vendor's console, available and supported now. That is a fair advantage to name out loud: it is turnkey today, while everything in this act runs against an upstream feature Red Hat has explicitly said it will not productize as a standalone server (3-act3-agentic.md). The honest claim isn't "we have agents and VMware doesn't", it's narrower: the correlation graph underneath is real, open and rule-based rather than a proprietary black box, so once an agent (Lightspeed, or anything else that speaks MCP) sits on top of it, that agent inherits every domain korrel8r already knows, not just the ones a vSphere-scoped tool was built to see.

Before you start

Full prerequisites, install order and every failure mode are in 0-prereqs-preflight-failure-modes.md. For this act specifically:

  • A reachable korrel8r 0.12.1. Either the in-cluster Deployment this evidence used, exposed through its own Route (evidence/korrel8r-0.12/deploy.yaml, route.txt), or the same binary run locally with korrel8r mcp talking stdin/stdout, confirmed real by korrel8r mcp --help and korrel8r web --help | grep -i mcp (evidence/act3-mcp/08-korrel8r-mcp-help.txt, 08-korrel8r-web-help-mcp-grep.txt). Local --help/version was run against binary 0.12.2-dev, close to but not identical to the deployed 0.12.1, that binary was only used to confirm the subcommand and flag exist, not to query the cluster.
  • A bearer token for the HTTP transport, $(oc whoami -t), and the same token to probe the GA COO pod's own /mcp for the contrast call, an unauthenticated request there returns 401.
  • The GA Cluster Observability Operator's korrel8r pod already exists in openshift-cluster-observability-operator if you want that contrast half, no separate install needed for it.
  • python3 -m json.tool or jq to read the responses, they arrive as SSE (content-type: text/event-stream), each reply is one data: line carrying the JSON-RPC body.
  • The VMCannotBeEvicted alert already firing on vm-non-migratable in demo-vms, staged the same way Act 2 stages it.

Steps

  1. Reach korrel8r 0.12.1. Locally, over stdio, using your existing oc login: korrel8r --config /path/to/korrel8r-standalone-config.yaml mcp. Against the deployed instance this evidence used, over streamable HTTP: 
    KORREL8R_URL=$(cat route.txt)   # e.g. https://<cluster-domain>
TOKEN=$(oc whoami -t)
  2. initialize, capture the session id header the response carries. 
    curl -sk "${KORREL8R_URL}/mcp" \
  -H 'Content-Type: application/json' -H 'Accept: application/json, text/event-stream' \
  -H "Authorization: Bearer ${TOKEN}" \
  -d '{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":"2025-03-26","capabilities":{},"clientInfo":{"name":"curl-evidence","version":"1"}}}'
# response header: mcp-session-id: <value>
SESSION=<value from that header>
  3. Send notifications/initialized to finish the handshake, then tools/list, every call after step 2 carries Mcp-Session-Id: ${SESSION} alongside the same headers as step 2. 
    curl -sk "${KORREL8R_URL}/mcp" -H "Mcp-Session-Id: ${SESSION}" ... \
  -d '{"jsonrpc":"2.0","method":"notifications/initialized"}'
curl -sk "${KORREL8R_URL}/mcp" -H "Mcp-Session-Id: ${SESSION}" ... \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/list"}'
  4. Call list_domains to see what stores korrel8r can actually reach. 
    -d '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"list_domains","arguments":{}}}'
  5. Call create_goals_graph from the firing alert, asking for the VMI, the pod, application logs and metrics. 
    -d '{"jsonrpc":"2.0","id":4,"method":"tools/call","params":{"name":"create_goals_graph","arguments":{
  "start":{"queries":["alert:alert:{\"alertname\":\"VMCannotBeEvicted\",\"namespace\":\"demo-vms\",\"name\":\"vm-non-migratable\"}"]},
  "goals":["k8s:VirtualMachineInstance.v1.kubevirt.io","k8s:Pod.v1","log:application","metric:metric"]}}}'
  6. Call get_objects on the pod query the graph just returned, no query written by hand. 
    -d '{"jsonrpc":"2.0","id":5,"method":"tools/call","params":{"name":"get_objects","arguments":{
  "query":"k8s:Pod.v1:{\"namespace\":\"demo-vms\",\"labels\":{\"kubevirt.io\":\"virt-launcher\",\"vm.kubevirt.io/name\":\"vm-non-migratable\"}}"}}}'
  7. Call get_objects on the log query from the same graph, limited to 5 lines. 
    -d '{"jsonrpc":"2.0","id":6,"method":"tools/call","params":{"name":"get_objects","arguments":{
  "query":"log:application:{\"namespace\":\"demo-vms\",\"labels\":{\"kubevirt.io\":\"virt-launcher\",\"vm.kubevirt.io/name\":\"vm-non-migratable\"}}",
  "constraint":{"limit":5}}}}'
  8. Run the identical step-5 request against the GA COO 1.5.2 pod's own /mcp (it listens on localhost:9443 inside its pod, reach it by oc exec or a port-forward, with Authorization: Bearer $(oc whoami -t)), and watch it stall at alert and metric.

Status

  • GA: nothing about the MCP transport itself. What is GA is the correlation engine underneath it, the Cluster Observability Operator's Troubleshooting Panel and its rule graph, shown working in Act 2.
  • Upstream, real: both MCP transports, korrel8r mcp for stdio and korrel8r web --mcp (default on) for streamable HTTP, Experimental since v0.10.0. The GA COO 1.5.2 image also answers /mcp requests, its bundled korrel8r 0.11.1 just can't cross from alert to VMI.
  • Experimental, demoed live: the full alert-to-VM-to-VMI-to-pod-to-log-to-metric walk over MCP, only reachable through the separately deployed upstream 0.12.1 instance, not the shipped console build.
  • Explicitly not shipping: Red Hat has stated it will not productize a standalone korrel8r MCP server.
  • Roadmap: OpenShift Lightspeed talking to korrel8r from inside the console, targeted OCP 5.1. Its agent-navigation feature-gate and the get_console/show_in_console tools are Dev Preview today.

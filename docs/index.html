OpenShift Virtualization observability, demo by demo

A VM's metrics, logs and network flows land in the same open, label indexed stores as every pod's and node's on the cluster: Prometheus and Thanos, Loki, and the network flow logs. That means you can join a VM's series to a pod's or a node's with plain PromQL, walk from a firing alert to the VM to its pod to its own logs in one correlation graph, and route that same alert into the automation pipeline you already run for containers. The four pages below each show one piece of that against a real, live cluster. The win here is not a prettier dashboard than vCenter's; it is where the data lives and what you can do with it once it's there.

Honest limits

Say these four things before anyone has to ask.

  • The GA Cluster Observability Operator ships korrel8r 0.11.1, which has no Alert to VMI rule. From a firing alert its Troubleshooting Panel graph reaches only the Alert and 128 metric series, not the VM, the pod or its logs (troubleshooting-panel/SUMMARY.md, reference-architecture.html).
  • Focus is disabled on the VirtualMachine, VirtualMachineInstance and Pod pages in this build. It only enables on the Alerting list page, and the workaround everywhere else is to type the korrel8r query straight into the panel's own query editor (screenshots/SCREENSHOTS.md).
  • The 24 hour OutdatedVirtualMachineInstanceWorkloads alert has never fired on this cluster, even though 21 VMIs have been outdated for at least 7 days straight, because both virt-controller replicas restart on leader election lease renewal failures and every restart resets the alert's timer (fleet-beat/SUMMARY.md).
  • Four PromQL details in the original deck do not hold on this build: the series-count join needs and on(namespace,pod) instead of group_left, the phase-transition histograms carry a phase label and no per-VM label at all, two claimed recording rules don't exist on 4.20.24, and kubevirt_vmi_last_api_connection_timestamp_seconds is labelled vmi, not name (act1-metrics/SUMMARY.md).

Where VMware still wins

OpenShift Virtualization has no What-If capacity modelling and no predictive DRS that forecasts load forward in time the way VMware's stack does. There is no built-in cost and chargeback layer in this architecture, and Prometheus and Loki are not built for the multi-year native retention that vCenter's long-term stores offer. Concede this before the rest of the pitch; it is what makes the case for joinable telemetry land instead of sounding like a sales pitch.

How this was built

This ran on a shared lab cluster that already had three bare metal workers and 28 other people's VMs running on it, 31 total once the demo's own three are added (act1-metrics/SUMMARY.md, fleet-beat/SUMMARY.md), on OpenShift 4.20.32, OpenShift Virtualization 4.20.24, Cluster Observability Operator 1.5.2. On top of that, an in-cluster LokiStack backed by MinIO, Network Observability, the Logging and Troubleshooting Panel console plugins, three demo VMs in their own demo-vms namespace, and a second, upstream korrel8r 0.12.1 running next to the operator's own 0.11.1 so the two could be compared side by side were added. Nothing outside the demo namespaces was changed, no node was rebooted, and the cluster's existing log forwarder was left alone. Everything is still deployed so it can be walked through live.
